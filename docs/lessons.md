# 教訓メモ

**要約**：作る前に前提を測ると無駄が消え、検証の穴（UI 層はホストでコンパイルできない・検証器自体が空振りする・断定は観測を超えやすい）が事故の大半を生む。測る対象にはコンテキストの固定費も含める（§6）。

このファイルは**追記でなく更新**する。新しい教訓が出たら該当行を書き換える／表に1行足す。

## 3. 測り方

- **1回の計測で A/B を判定しない。** 3回以上回して分布で見る。JointLNS は壁時計予算で動くので
  run 間に幅が出る（real の既知帯 49213〜49232）。同一 JVM 内の実行順でも変わる。
- **A/B は同一スクリプト内の連続実行で比べる。** 「決定的」と思っていた golden も、機械の負荷が変われば
  2469→2490 と動く（壁時計予算の JointLNS 由来）。別々のタイミングで測った2つの数字を並べて
  「改善した／退化した」と言わない。3.340.0 は同一スクリプト内の連続 A/B で3件とも一致を確認した。
- **時間を使っている場所と、成果を出している場所は別。** 3.339.0 で「後処理の27〜42%を占める」と分かった
  パスを、削る前に**何にその時間を使っているか**測ったら、8回の呼出すべてで最後の改善後に
  32〜60ステップが空回りしており、さらに最良を保持せず捨てていた（3.340.0）。
  一方で ablation では実際に効いていた＝**遅い＝無駄ではない**。削るか直すかは ablation で決める。
- **`weighted` を見る。`c1` 単体で判断しない。** 目的関数は hard → weightedScore → total の順で、
  c1 2件を手放して low(90) 5件を消す取引は正しい改善。族の件数だけ見ると悪化に見える。
  （重みの数値はここに書かない＝HF77 で変わると取り残される。現在値は `docs/business-logic.md` の重み表。）
- **前提の確認と効果の確認は別物。** 「focus が一度も選ばれていない（0/20）」が鮮やかに確認できても、
  下流が同じ情報を別経路で持っていれば直しても効かない（3.310.1 で実測）。
- **反実仮想は出荷せずに測れる。** データを書き換えず、緩めた版で研磨だけ回して差を見る。
- **「余っている資源を使えば得」も直感。** 予算の54%が余っているのを見て追加精製へ回したが、
  +17秒で中立だった（3.341.1）。資源が余っていることと、それを使って改善できることは別。
- **有意でない差を「改善」と書かない。** 早期終了の撤去は中央 −3.5% だが U検定 p≈0.075。
  分布の幅（326）に対しサンプル5では示せない。示せなかったことを結論として書く。

| v6 エンジン・model | **できる** | ホスト JVM で実コンパイル＋JUnit 実行（`tools/host/hosttest.sh`。`kotlin-compiler-embeddable` は初回に Maven Central から取得＝コンテナが作り直されても再現できる。3.497.1）。実データ3件で最終盤面の不変も確認。**バグ注入で検証するときはハーネスの第1引数にそのツリーを渡す**（既定は本体を見るため空振りする） |
| C++ / JNI | **できる** | `tools/native/host_parity_bench.cpp` を g++ で実ビルド・実行（mismatch=0）。CI にも配線済み |
| UI（Compose）・ViewModel・WorkManager | **できない** | 括弧均衡・シンボルのスコープ逆引き・呼び出し側シグネチャの静的確認まで。**最終判定は CI**。実行の所有権・kill 復元のような並行性はエミュレータ/実機でしか確かめられない |

**実機のログが得られない前提で作る**（3.550.0）。Godot 版 APK が「起動直後にクラッシュ」と報告されたが logcat は来ない。
机上の消去法（ELF 整列・API 整合・PCK 解決・例外の捕捉経路）では候補が 4 つ残り確定できなかった。
次から同じ状況で二手目に迷わないよう、**起動段階のマーカー＋未捕捉例外のファイル記録＋次回起動時の診断画面**を
アプリ自身に持たせた（`MagiStartupGuard`）。「どこまで到達したか」だけでもネイティブクラッシュの切り分けになる。
結果、同じ版で起動に成功したため原因は確定できなかった（3.551.0）。**回避策と診断を同時に入れると、直った時に
どちらが効いたか分からない**。急ぐ場面では許容するが、記録には「未特定」と書く。

**Godot は端末ピクセル 1:1 で描く**（3.551.0）。Compose の dp 感覚で作ると高 DPI 実機で文字が 1/2.5 になり、
安全領域（ステータスバー・カメラ穴）も自動では避けない。エディタで見えないので、`content_scale_factor=DPI/160` と
`get_display_safe_area()` を最初の実機スクリーンショットの前に入れておくべきだった。
（3.552.0 追記）その修正も一発では効かなかった。`project.godot` の enum 設定は**整数で書く**（文字列は `int()` で 0 に化け、
エラーも出ない）。`get_display_safe_area()` は Android ではカットアウトだけ＝システムバーは含まない。**Godot の API は
名前から想像せず、`platform/android/` の Java 実装まで読む**（`GodotIO.java` は短い）。あわせて、実機の判別材料
（版・画面 px・DPI・倍率・余白）を画面に出しておくと、次のスクリーンショット 1 枚で「効いた／効かない／別の APK」が分かる。

**穴はここ**：UI 層は静的チェックが通ってもコンパイルが通る保証がない（#1・#17 がその実例）。
括弧均衡とスコープ逆引きは**構造**しか見ない。**名前**（プロパティ・関数のシグネチャ・多重定義の
どちらを呼ぶか＝#46）は別途モデル/ヘルパーの宣言と突き合わせる。
機械的な一括編集をしたら、**エンジン層は必ずコンパイルまで通してから次へ進む**（型の不整合・引数の重複は
コンパイラだけが見つける。3.326.0 は18関数への一括配線で「引数を二重に渡した」等を実際にコンパイルで捕まえた）。
CI を起動したら**結果を確認するまで次へ進まない**。「CI 待ち」と書いて別の作業を始めた結果、
失敗に気づくのが1ターン遅れた。

**検証器そのものを疑う**（3.409.4 で実際に踏んだ）。教訓#30（防具が本当に発火するかバグを注入して確かめる）を
実行するとき、`hosttest.sh` はリポジトリルートを**直書き**していたため、scratch へコピーしてバグを入れても
**本体をコンパイルしていた**＝「0 failures」が出て検証が空振りした。しかも**空振りは成功と見分けがつかない**。
ハーネスを第1引数でルート差し替え可能にして再実行したところ、注入したバグでちょうど1件が落ちた。
同型の失敗は `hosttest.sh` のコンパイルエラー検出（`^e: ` だけを見て `error:` を見逃し「Tests run: 0」を
成功と表示した・3.406.0）でも踏んでいる。**検証が「何も起きなかった」と言ったら、まず検証器が対象を
見ているかを確かめる。** 対照的に `design_lint.py` は自分の位置からルートを導くので scratch 検証が正しく効いた
＝**ツールは実行位置でなく自分の位置から対象を決める**のが正しい（3.409.1 で 5 ツールを同じ形へ配線した）。

## 6. コンテキストの固定費と変動費（3.468.0 で測って優先順位が入れ替わり、3.470.0 で完了）

**「AIレビューをしやすくしたい」の具体的な困りごとがコンテキスト圧迫なら、まず固定費を測る。**
聞く前に「Godファイル（`V6HotfixPasses` 4,682行）の分割」を P3 に置いていたが、測ったら的が外れていた。

| | 大きさ | いつ効くか |
|---|---|---|
| `CLAUDE.md` | **422k-tok** | **毎ターン固定**（プロジェクトメモリは全文が入る） |
| `V6HotfixPasses.kt` | 93k-tok | そのファイルを読んだターンだけ |
| main の全 Kotlin | 648k-tok | — |

しかも `CLAUDE.md` の内訳は**恒常ルール 30k に対し版数付き作業記録が 9割**。
**固定費を毎ターン払いながら、変動費 93k のファイルを分割しようとしていた。**
分割してもレビュー時に読むのは元々関数単位（`sed -n` / `grep -A`）なので、読む範囲は変わらない
（「変更の局所化」という別の利点は残る＝目的が違う）。

対処は**索引化**＝本文を `docs/history/` へ移し、**原文見出しのまま**の索引だけ CLAUDE.md に残す（422k→202k）。
要旨へ削ると見出しの補足版数（3.301.1 / 3.308.1 / 3.322.0 等）が索引から消えてその版で引けなくなることを
実測してから全文へ切り替えた。**内容は1行も捨てない**（非空行の多重集合一致で検証）。

**リスクは「読まれなくなって再発すること」**。作業記録は「測って否決した案・同型のバグ・決定記録」の資産で、
実際 3.419.0 / 3.386.0 / 3.385.0 の記録が判断を決めた場面がある。CLAUDE.md 冒頭に
「同じ領域を触る前に必ず索引を検索する」と引き方・新記録の書き方を明記して緩和したが、
**仕組みでなく指示なので確実ではない**＝そこは正直に書く。

**3.470.0 で完了**（202k→約54k-tok・5,515行→1,303行）。3.468.0 は 203 節を移したが**まだ 148 節・
本文の 83% が残っていた**＝「半分だけやって完了と呼ぶ」状態だったので、残りを全部出した。
このとき **決定記録 D4/D5/D6 が版数付き節の中に埋もれていた**ことに移動前の走査で気づいた
（そのまま移すと「再提案しない」と決めた内容が毎ターンの視界から消える）。恒久節へ持ち上げ、
本文にしか無かった D7/D8/E5 も1行ずつ起こした。**分離の規則は「見出しに版数があるか」だけ**にして、
「これは恒久か記録か」という判断を入れなかった＝機械的に検証できる形に保った
（判断が要る 610 行ぶんは分けて残し、次の候補として明記した）。

**一般化**: 「重い」と感じたものを測る前に直さない。固定費（毎ターン払う）と変動費（読んだときだけ）を
分けて数え、固定費から削る。§2 の「測ってから作る／作らない」をコンテキストにも当てる。

**第2巡（3.497.3）**: 3.470.0 で 54k まで下げた本体が、その後も「恒久の事実だけ」を名乗りながら約 5.8 万トークンあった。
節ごとに測ると、作業記録の**索引 1.9 万**＋ネイティブ加速 3 節 1.6 万＋停滞脱出 0.6 万＋ドッグフーディング/後処理研磨 0.4 万
＝**版数付きの叙述が 4.5 万**を占めていた。索引を `docs/history/INDEX.md`、叙述を `docs/history/topics.md` へ出し、本体には
各 3〜5 行の恒久事実だけを残して **190KB→39KB（約 1.2 万トークン）**。判定の物差しは「段落に版数が付いていれば本体に置かない」。
引き方（grep）は変えていないので運用は同じ。外部の2記事（3層ドキュメント設計／on-demand 化）が指す先はここだった。

**大きな移動をするときは、移す側に「移してはいけないもの」が紛れていないかを移動前に走査する**
（決定記録・不変条件・再提案しない判断は、量が少ないぶん埋もれやすい）。
